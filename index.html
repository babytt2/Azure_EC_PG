02 / ARCHITECTURE구조 설명

PostgreSQL 안에서 동작하는 Citus

03 / WORKLOAD DESIGN설계 고려사항

어떤 Workload에 적합한가

Workload설계 모델확인할 점
Shared-table SaaSTenant Key Row Sharding · ColocationPK/FK, Hot Tenant, Cross-shard Write
Schema-per-tenantSchema Shardingsearch_path, Schema 수, Cross-schema SQL
IoT / EventEntity 기반 Distributed IngestionHot Key, Index, Batch
Real-time AnalyticsParallel SQL · Distributed AggregationFan-out, Shuffle, Memory, OLTP 경합

Distribution Key Predicate와 Table Colocation은 Network Round Trip과 Cross-shard 연산을 줄이는 데 유리합니다. 반대로 Fan-out과 Data Movement는 비용을 늘릴 수 있습니다.

테이블 생성만으로 자동 분산되는 것은 아닙니다. MVU도 잘못된 Shard Key, Hot Shard 또는 SQL Compatibility 문제를 해결하지 않습니다.

장표에 기재된 제약: Node-count Scale-in, Single User Database, Extension / SQL / 관리 기능 제약. 실제 적용 시 최신 제품 문서를 확인해야 합니다.

04 / MVU SCOPE동작 범위

무엇이 바뀌고, 무엇을 확인해야 하나

PostgreSQL Engine

17.11 → 18.6

Binary, Catalog, SQL / Type / Index / Extension Compatibility와 Statistics / Query Plan

Citus

13.3 → 14.1

Target Engine에 맞는 Extension, Planner / Executor, DDL / Distributed Transaction

Cluster State

Metadata · Placement

Node / Shard, Reference Table, Colocation, Connectivity, HA / Replica

이번 실측 Endpoint, Topology, SKU, Storage, Public Access와 Shard Placement가 유지됐으며 Node Connectivity는 4/4였습니다. 다만 version-only 요청에서 Entra Auth 설정 초기화를 관찰했습니다.

일반 MVU 문서의 흐름과 이번 실측의 경계

일반 MVU 문서는 Precheck → Implicit Backup → pg_upgrade → 오류 시 이전 버전 복구 시도 흐름을 설명합니다. Elastic 내부의 Node Shutdown 순서, pg_upgrade 시작/종료, Disk Copy / Clone 방식, 임시 Compute / Storage, DNS 내부 Target, HA Sequencing은 이번 테스트에서 확인하지 못했습니다.

Rollback과 복구는 검증했나요?

장표는 성공 후 in-place rollback이 없는 것으로 설명합니다. PITR / 새 Cluster 복구를 검토해야 하지만, 이번 테스트에서는 Rollback과 PITR 복구 모두 시험하지 않았습니다. 별도 복구 Rehearsal이 필요합니다.

08 / RECOVERY FINDINGS관측과 추론 분리

Reconnect 이후 확인한 Data · Auth · Logs

Data: COMMIT 응답을 받은 분산 쓰기 20건이 이후 조회되지 않음

관측: 13:53:09.5–13:53:16.6 사이 Distributed Write 20건이 해당됩니다. 기존 1,402,000 Rows는 보존됐습니다. Shell Table Statistics는 Node 1에 17 Rows, Node 2에 3 Rows였습니다.

추론: Metadata 준비 전에 Shell Table에 쓰기가 기록됐을 가능성입니다. 누락 ID의 실제 Row-level 존재 여부, 근본 원인, 공식 복구 절차는 미확인입니다. 원인을 확정하거나 제품 전반의 데이터 손실로 일반화하지 않습니다.

Auth: version-only PATCH 이후 신규 Entra Login 실패

관측: 13:57:07.9에 pgaadauth 관련 설정 9개가 Default로 초기화됐습니다. 기존 Session은 유지됐지만 신규 Login은 실패했습니다. 14:03:16 재활성화 후 14:03:37 정상화됐습니다.

별도 시험: PATCH에 authConfig를 포함한 1회 시험에서는 설정이 유지됐습니다. 모든 환경에 대한 해결 보장이 아니며, 의도된 동작인지 Bug인지도 제품팀 확인이 필요합니다.

Node: 함께 Restart된 것으로 관측되지만 내부 순서는 미확인

PG18 시작 시각은 Node 1 13:53:09, Node 2 13:53:13입니다. 두 Node를 함께 내린 것으로 해석했지만 내부 Orchestration Sequence나 Rolling 여부를 공식 동작으로 확정하지 않습니다.

Logs: Upgrade 내부 단계의 가시성 제한

Activity Log에서 요청 시작/수락은 확인했으나 최종 Success / Failure Event는 확보하지 못했습니다. Log Analytics는 Node 2 13:53:25 이후, Node 1 13:54:20 이후 확보됐고 Shutdown / pg_upgrade / Startup 구간 로그는 확보하지 못했습니다.

운영 증적은 Azure-AsyncOperation, Resource State와 Client Probe를 함께 수집하는 방식으로 보완합니다.

09 / BLOCKER TESTS별도 1-node 시험

Upgrade가 실행되지 않아도 원인이 충분히 반환되지 않을 수 있음

Japan East 1-node PG17.11 Cluster에 7가지 Blocker를 함께 구성했습니다: Logical Replication Slot, Prepared Transaction, pg_stat_activity 의존 View, pg_stat_statements 의존 View, User Event Trigger, hypopg, pg_diskann.

Trial조건관측 결과
1Blocker 7개 존재2분 36초 후 Ready · PG17 유지. 중단 없음, Activity Log 최종 결과 미확보

11 / QUESTIONS제품팀 확인 필요

고객 FAQ와 아직 답이 확정되지 않은 질문

Q. DB 접속이 되면 바로 Write를 열어도 되나요?

권고하지 않습니다. Resource Ready 이후 Metadata / Data Consistency / 신규 Auth / Application SLO 검증까지 통과한 후 재개하는 절차를 제안합니다.

Q. 예상 중단 시간을 7분으로 안내해도 되나요?

아니요. 7분은 한 환경의 DB Outage Proxy입니다. 실제 업무 중단, HA 복구, 대규모 데이터 또는 다른 Workload에 대한 예측값이 아닙니다. 고객 환경 Rehearsal로 변경 창을 정해야 합니다.
